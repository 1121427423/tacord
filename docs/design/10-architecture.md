# 10 · 技术架构（含 macOS / Apple Silicon 方案）

## 10.1 选型结论（先给答案）

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 引擎 / 编辑器 / 渲染 / UI | **Godot 4.7.2**（已钉；4.8 仍在 dev） | MIT 许可；**原生 arm64 macOS 编辑器**；Apple Silicon 上有**原生 Metal 后端**（4.4 起，仅 arm64），Intel Mac 走 MoltenVK；内置导航、物理、动画、UI、导出模板 |
| 模拟核心（AI / 掩体 / 弹道 / 经济） | **独立库 `sim_core`**，不依赖引擎，可被 headless CLI 与 CI 直接跑 | AI 是本项目 80% 的复杂度与风险，必须与表现层解耦，才能确定性回放、批量测试、并行优化、将来做服务器权威 |
| `sim_core` 语言 | **首选 Rust**（`gdext` 绑定，5.1k★，2026 年仍活跃维护）；**备选 C++20 / godot-cpp** | 数据导向、无 GC 抖动、`rayon` 并行、内存安全；`cargo test` + `proptest` 直接跑在 CI |
| 绑定方式 | Rust `cdylib` → GDExtension（`gdext` 0.5.5）；若 `gdext` 在某版本卡住，**退路**：`cbindgen` 导出 C ABI，用一层薄的 C++ GDExtension 包装 | 把"绑定风险"限制在一个可替换的薄层里 |
| 绑定目录 | `gdext/`（**独立 workspace**，绝不能并入 `sim/`）；`godot/` 只放工程、场景与 GDScript | A6 边界：CI grep 强制 `sim/` 内无 godot |
| API 绑定 | CI 用 `--features api-custom` + `GODOT4_BIN` 指向真实 4.7.2 生成绑定 | gdext 预置的 API 是 4.6，直接用会走兼容层（"API v4.6 / runtime v4.7.2"）—— 能跑，但不该依赖 |
| 脚本层 | GDScript 只做**胶水**：UI、相机、特效、音频触发、关卡装载 | 保持热重载的迭代速度；所有游戏规则一律在 `sim_core` |
| 多人 | **确定性 Lockstep + 命令延迟**（输入只有命令，频率低，天然适合 RTS 式同步） | 支持回放、观战、断线重连、反作弊校验；见 §10.9 |

> 决策点 D-1（Rust vs C++）、D-2（定点 vs 浮点）见 `90-roadmap-acceptance.md`。默认按 Rust + 定点执行。

### 10.1.1 为什么不选其他方案

| 方案 | 否决原因 |
| --- | --- |
| Unreal 5 | 编辑器和着色器编译在 M 系列上迭代慢；Nanite/Lumen 对低多边形俯视 3D 是负担；授权与包体成本高 |
| Unity 6 | 技术能力足够（DOTS/ECS 适合大规模 AI），但许可政策与编辑器体积/启动成本对 1–2 人团队不友好；金属后端成熟是加分项 |
| Bevy / 自研 wgpu | 数据导向 ECS 天然契合本项目，但编辑器、动画、地形与美术工具链要全部自研，工期风险不可接受 |
| 纯 GDScript | 400 单位 ×30Hz 的射线级模拟无法达标（解释器开销 + GC 抖动） |
| Godot C# | macOS 公证需要 JIT entitlement，Hardened Runtime 下摩擦大；且我们需要的是"引擎无关的 sim"，不是更快的脚本 |

## 10.2 macOS / Apple Silicon 专项

这是"一等公民"承诺的落地清单，逐条都要有人负责。

### 10.2.1 渲染后端
- **默认：Metal 后端**（Godot 4.4+ 提供，仅 Apple Silicon）。在 `boot` 时探测：支持 Metal 的 arm64 设备 → `--rendering-driver metal`；否则回退 MoltenVK（Vulkan）→ 再回退 Compatibility（GL，仅 Intel Mac 应急）。
- 提供启动参数与设置项 `video/driver: auto|metal|vulkan|gl`，玩家可手动覆盖，崩溃两次自动降级并写日志。
- **禁止**依赖硬件光追、mesh shader、bindless（Metal 3 有部分能力但 Godot 封装不可控）。
- Tile-based GPU 注意：减少全屏 pass 数量，后处理合并为 1–2 个；避免不必要的 `render_target` 读写回。

### 10.2.2 内存（统一内存架构，8GB 是硬约束）
| 预算项 | 上限 |
| --- | --- |
| sim 状态（400 单位 + 世界柱 + 掩体缓存） | ≤ 384 MB |
| 几何（chunk 网格 + 实例） | ≤ 1.5 GB |
| 纹理（ASTC 压缩，Metal 原生） | ≤ 1.0 GB |
| 音频（流式，短音效常驻） | ≤ 256 MB |
| 渲染 target（1080p，含阴影图） | ≤ 400 MB |
| **合计（M1 8GB 目标）** | **≤ 3.5 GB** |

- 统一内存没有独立显存，CPU/GPU 共享带宽：**避免 CPU 每帧回读 GPU 数据**（如 GPU 拾取、读回缓冲）；拾取一律在 CPU 侧用 sim 的柱数据做射线。
- 柱数据用 SoA + 分块 RLE；远景 chunk 只保留碰撞/掩体用的精简层（"碰撞 LOD"），不保留渲染网格。

### 10.2.3 CPU 与调度
- Apple Silicon 有性能核/能效核：**不要用 `num_cpus` 盲目起满线程**。用 `rayon` 的默认线程池（会读取逻辑核数），但对长任务启用 QoS（`pthread_set_qos_class_self_np`/`dispatch` 默认继承），并在"省电模式"下把 job 线程数限制到性能核数量。
- 帧率上限默认 60（可选 30 / 60 / 120 / 不限制）；后台自动降到 30 并把 AI tick 降到 15Hz。
- 热节流：监测帧时间滑动窗口，连续 2 秒超预算 → 依次降级：后处理 → 阴影级数 → 单位渲染距离 → AI LOD 距离 → 分辨率缩放（最低 0.75x）。

### 10.2.4 打包、签名与公证
- 导出 **arm64-only** app bundle（`macos` 导出模板，arch=arm64）。不做 universal2（体积翻倍、且我们不支持 Intel）。
- Hardened Runtime + `codesign --timestamp`；提供两条通道：
  - **开发/分发的 ad-hoc 签名**：`codesign -s -`，能在本机与已授权机器运行；
  - **正式分发**：Developer ID Application 签名 + `notarytool` 公证 + stapling（需要 Apple 开发者账号，$99/年）。CI 里通过 secrets 注入证书，未配置时自动产出 ad-hoc 版本并标记为未公证。
- 必要 entitlements：`com.apple.security.cs.allow-jit`（仅当绑定层需要）、`com.apple.security.device.audio-input`（若做语音）、`com.apple.security.files.user-selected.read-write`（关卡/回放导入导出）。**若用 Rust/C++ 而非 C#，则不需要 JIT 权限**，这是选 Rust/C++ 的一个附加收益。
- `.dmg` 采用简单的拖拽式布局；同时提供 `.zip`。Gatekeeper 首启动说明写进 README。

### 10.2.5 构建矩阵与 CI
**三平台校验和一致（A1）必须有真实的 CI 矩阵支撑**（R9）——原矩阵缺 Windows，等于验收无法执行。

| Runner | 任务 | 频率 |
| --- | --- | --- |
| `ubuntu-latest` | `cargo test`（单测 + 属性测试）、`cargo bench`（性能回归）、**黄金回放 + 校验和**、Godot headless 冒烟、Linux 构建 | 每次 push |
| `windows-latest` | **同一批黄金回放 + 校验和**（与 Linux 结果逐位比对）、`cargo test`、Windows 构建 | 每次 push |
| `macos-15`（arm64，固定版本避免 `macos-latest` 漂移） | **同一批黄金回放 + 校验和**、构建 arm64 app bundle、签名、`.dmg`、启动自检（打开 → 跑 30 秒 → 退出码 0 → 日志无 ERROR） | 每次 push |
| `macos-26`（arm64） | 前瞻验证（可选，允许失败） | 每周 |
| `ubuntu-latest` + Godot Web 模板 | 导出 Web 版本推到 Pages（**仅**用于逻辑/UI 走查，性能不代表真机） | 每次 push |

- **跨平台一致性怎么判**：三个 runner 各自把黄金回放的 `final_checksum`（以及每 1800 tick 的快照哈希列表）
  作为 artifact 上传，一个汇总 job 比对三者**逐位相同**，不同即失败。这样"定点数学在某平台行为不同"会被立刻抓到。
- 沙箱开发机是 **Linux x86_64**，无法产出/验证 macOS 构建。因此：**所有能在 Linux 上验证的东西（sim、逻辑、回放、bench）都必须在 Linux 上验证**，macOS runner 只负责"打包 + 能启动 + 跑同一批回放"。这是本项目的测试策略基石。
- 参考：GitHub 的 `macos-15` / `macos-26` / `macos-latest` 标签都是 **arm64**（Apple Silicon），macOS 26 runner 已于 2026-02 GA；需要的 Intel 变体是 `macos-15-intel`（我们不用）。

## 10.4 确定性模拟核心

### 10.4.1 时间步进
| 层 | 频率 | 内容 |
| --- | --- | --- |
| 渲染 | 显示刷新率（自由） | 插值 sim 状态、粒子、UI |
| **Sim tick** | **固定 30 Hz（33.33ms）** | 移动、弹道、物理、感知、AI 执行、经济 |
| 感知更新 | 10 Hz（每 3 tick） | 视线检测、听觉事件、contact 更新 |
| 掩体评估 | 5 Hz（每 6 tick） | 候选掩体打分、姿态决策（事件可打断） |
| 班组层 | 2 Hz | 角色分配、跃进节奏、救援调度 |
| 指挥层 | 1 Hz | 目标选择、兵力分配、补给与建造优先级 |
| 掩体/导航重建 | 事件驱动 + 摊还 | 柱被破坏 → chunk 标脏 → 每帧最多重建 2 个 chunk |

- 所有"低频系统"用**摊还调度**（分桶：每 tick 处理 1/N 的单位/班组），保证单 tick 峰值可控。事件（受伤、发现敌人、命令变更、掩体失效、掩体被毁）可**立即触发**重算，绕过摊还。

### 10.4.2 定点数学（`sim_math`）
- 位置：`i32`，单位 **毫米**（±2147 km，1mm 精度）。
- 方向/角度：`u16`（0..65535 ≡ 0..2π）。
- 标量（速度、概率、系数）：`Q16.16` 的 `i32`（±32767.99998，精度 1.5e-5）。
- 三角/开方：查表 + 线性插值（`sin` 4096 项表 + 插值），`atan2` 用定点多项式。**不使用 `libm`**（跨平台/跨编译器的 `sin/sqrt` 可能有 1ulp 差异，会毁掉 lockstep）。
- 随机：每个系统一条独立的 `xorshift128`/`pcg32` 流，seed 来自 `(level_seed, system_id, entity_id, tick)`，保证并行执行顺序无关。
- 编译约束：`-C opt-level=3`，**禁用**任何 fast-math（Rust 无此开关，天然安全）；禁止在 sim 里使用 `f32/f64`；用 `#[deny]` + CI grep 强制。

> **退路（方案 B，见 D-2）**：若定点改造成本过高，则 sim 用 `f64` + 严格纪律（固定同一编译器版本、禁用 FMA 收缩、统一 libm、CI 三平台校验和比对），并**放弃 lockstep**，改用服务器权威快照同步。代价：回放/bench 的价值下降、多人带宽上升。不推荐，但保留。

### 10.4.3 数据布局
- 自研 SoA（不是通用 ECS 框架）：每个系统拥有自己的列式数组（`positions: Vec<Vec2i>`, `postures: Vec<Posture>`, ...）。理由：sim 的实体种类少、生命周期简单，自研比通用 ECS 更易确定性排序与内存预算。
- 实体句柄：`u32`（index 24bit + generation 8bit），失效句柄访问在 debug 下 panic。
- 命令缓冲：AI 决策阶段只写入 `CommandBuffer`，在 tick 末统一 apply，保证并行阶段无别名写入。

### 10.4.4 并行
```
tick 内阶段（阶段内并行，阶段间串行）：
 1. 输入            （应用玩家命令 / 网络命令）
 2. 世界事件摊还    （dirty chunk 重建：掩体槽、导航代价、碰撞层）
 3. 感知            （批量射线 rayon 并行 → contact 增量）
 4. 决策            （指挥层 → 班组层 → 士兵层；按 squad 分片并行，写 CommandBuffer）
 5. 执行            （移动、弹道、动作状态机；并行，写 CommandBuffer）
 6. 结算            （伤害、压制、士气、经济、胜负判定；串行）
 7. 校验和          （每 30 tick 计算一次 sim 状态哈希）
```
- 目标：400 单位时，阶段 3–5 在 M1 上并行后 **≤ 8ms/tick**（见 §10.7 预算）。

## 10.5 世界表示

- **体素柱（Voxel Column）**：XZ 平面 0.5m 栅格，每根柱记录：
  ```
  height_mm: i32          // 实体顶面高度（地面或建筑顶面）
  material: u16           // 索引 materials.ron
  hp: u16                 // 结构强度（破坏用）
  flags: u8               // SOLID / DESTRUCTIBLE / CLIMBABLE / TRENCH / WATER / DOOR / TUNNEL ...
  occupancy: u8           // 被单位/工事临时占用的标记（不阻挡视线时可忽略）
  ```
  多层结构（二楼、桥、窗户）用 **segment list**（每柱 1–4 段 `{bottom_mm, top_mm, material, hp}`，**段之间允许空隙**）。
  段列表 + 空隙已经能表达：二楼楼板、窗户空洞、**悬挑/阳台/桥下可通行空间**（例如 `[0,3000 实体] [3000,5000 空] [5000,5600 实体]`）。
- 地图规模：**1024 m × 1024 m → 2048×2048 = 4.19M 柱**。按 32×32 chunk 分块（64×64 = 4096 chunk）。尺寸为 2 的幂（1024=2^10 m / 0.5=2^-1 m / 32=2^5），索引与空间哈希全部可用位移实现。空旷地面柱用 RLE 压缩，实测目标 ≤ 62 MB（CI 自检 `tools/check_constants.py` 会校验内存估算）。
- **破坏**：伤害 → 减少段 hp → 归零则该段消失（或降级为"残骸段"，高度减半）→ chunk 标脏 → 触发掩体槽、导航代价、渲染网格的局部重建。
- **挖掘**：战壕是"降低柱高度 + 标记 TRENCH"，与破坏共用同一条修改管线（这是让"挖战壕"真实存在的关键）。
  地道的几何部分同理（挖出负高度段 + 标记 TUNNEL），但它的**连通性由显式图描述**，见下。

### 10.5.1 几何表示的能力边界与分工（R4）

柱模型有明确的表达上限，必须有意识地接受它，而不是假装它能表示一切：

| 需求 | 柱模型能否表达 | 处理 |
| --- | --- | --- |
| 墙、箱子、车、残骸、战壕、弹坑 | ✅ 原生 | 直接由段派生掩体 |
| 二楼/楼板/窗户 | ✅ | 段列表 + 空隙 |
| **悬挑、阳台、桥下通行** | ✅ | 段之间有空隙即可（上式） |
| **斜面 / 斜坡 / 屋顶坡面** | ⚠️ 阶梯近似 | 0.5m 栅格下以阶梯表示；**美术约束**：可行走斜面坡度 ≤ 30°，视觉网格保留真实斜面，但体素代理按阶梯。玩家不会注意到，因为掩体判定用的是体素 |
| 曲面、不规则残骸 | ⚠️ 体素代理 | 视觉网格可以是任意形状；**判定只认体素代理** |
| 极薄的遮挡物（铁丝网、栅栏） | ✅ 特殊材质 | 半透：阻挡移动、只部分阻挡视线与子弹（材质表带 `blocks_sight` 系数） |

**权威几何 = 体素柱**：掩体派生、LOS、弹道、破坏、导航代价**一律只走体素**，不碰渲染网格。
**渲染网格是表现**：可以任意精细，但必须遵守一条铁律 ——

> **凡是"能当掩体、能挡子弹、能被炸掉"的东西，都必须有体素代理；纯装饰物可以只有三角网格。**
> CI/工具检查：每个可破坏/可掩体的渲染物件必须关联至少一个柱段（`tools/check_geo.py`，M3 引入）。

若将来实现中发现阶梯近似不可接受（例如玩家抱怨斜坡上掩体判定诡异），退路是**混合碰撞**：
体素继续负责掩体/破坏/射线，另加一层凸包用于动画落脚与载具碰撞。这是 T1 级改动，不进 1.0。

### 10.5.2 导航：2D 流场 + 显式图（R4）

单一 2D 导航无法表达"一楼/二楼/地下"三种空间在同一 XZ 上共存。冻结为混合表示：

| 空间 | 表示 | 说明 |
| --- | --- | --- |
| 地表 / 单层 | **2D 代价场 + flow field**（每柱一个可行走高度 = 该柱最高可站立顶面） | 大群体移动便宜，与威胁场（§20.2.5）同一张栅格，可直接叠加代价 |
| 建筑内部（1.0 支持到 2 层） | **显式导航图**：节点 = 门/楼梯/窗/房间中心，边 = 可通行连接 | 节点由体素自动候选（每个门洞/楼梯生成节点），边由生成器或关卡数据连接 |
| **地道网络** | **显式 `TunnelGraph`**（见下） | 连通性是设计出来的图，不是从体素派生的 |

两层通过**接口节点**连接（门口 = 地表节点 ↔ 室内节点；地道入口 = 地表节点 ↔ 地下节点），
寻路时先在同一层内用 flow field / 图上 A*，跨层时走接口节点。

**地道数据模型**（这是原设计缺失的部分）：

```
TunnelGraph {
  nodes: [ TunnelNode { id, pos: (Mm, Mm), depth_mm: i32,   // 负高度
                        kind: ENTRANCE | JUNCTION | CELL | EXIT,
                        links: [node_id; ≤4], collapsed: bool } ]
  owner: Team
}
```

- **进入/离开**：单位在 ENTRANCE 节点下潜（1.0s）→ 在图上按边移动（速度 0.9 m/s）→ 在 EXIT 节点上浮（1.2s 冒出，暴露窗口）。
- **为什么不可见**：这不是靠"隐藏标记"，而是**几何自然结果**——地下段位于地表实体段之下，
  地面单位的 LOS 射线被地表柱挡住。reveal 的唯一途径是发现入口（看到敌人下去 / 侦察 / 口供 / 监听挖掘声）。
- **炸塌 = 删边**：`collapsed = true` → 图断开 → 通道被封；内部单位被困（可等待工兵挖通：`collapsed = false`，耗时 20s）。
  这一步只改图，不动体素，因此代价极低且完全确定性。
- **牢房（CELL）** 与俘虏系统（§40.2.4）通过节点 kind 关联。

## 10.6 渲染与表现（Godot 侧）

| 项目 | 方案 |
| --- | --- |
| 地形/建筑网格 | 每个 chunk 做 surface-nets/greedy 网格化，生成静态 `ArrayMesh`；破坏只重建脏 chunk，**每帧最多 2 个**（预算 1ms） |
| 单位 | 角色 ≤ 3000 三角、≤ 30 骨骼；用 **MultiMesh/InstancedMesh + 骨骼动画烘焙到纹理（bone texture / VAT）**，每阵营每 LOD 1 个 draw call；近景（≤ 30m 且 ≤ 12 个）切真实 `Skeleton3D` 以获得精细动画 |
| 阴影 | 单方向光 + CSM 3 级（2048/1024/512，覆盖 400m）；单位用 blob/contact shadow 补充 |
| 后处理 | 至多：TAA/FXAA + 色调映射 + 轻微暗角；**不用 SSAO**（用烘焙 AO + 接触阴影代替） |
| 可读性（俯视 3D 的生命线） | ①脚下阵营环（可关）；②被建筑遮挡时用 **X 光描边** shader 显示单位轮廓；③曳光弹 + 弹着尘土 + 枪口焰；④按住 Alt 显示附近掩体槽评分热力；⑤选中单位显示视锥、目标、威胁箭头；⑥AI 调试层（F1–F4：掩体图 / 威胁场 / contact 表 / 当前任务与评分） |
| 相机 | 斜俯视轨道相机：俯角 20°–75°、距离 15–120m、WASD/边缘平移、滚轮缩放、双击单位跟随；"Cinematic"只读跟随（肩后/头顶），不改变控制方式 |

## 10.7 性能预算（Apple Silicon）

**目标**：M1（8GB）1080p / 60fps / 400 单位同屏；M4 Pro 1440p / 120fps / 800 单位。

**口径统一（R8）**——三份预算曾经混用"每帧/每 tick"，这里一次性定死：

| 口径 | 周期 | 定义 | 用途 |
| --- | --- | --- | --- |
| **每 sim tick** | 33.33 ms（30 Hz） | 一次完整模拟步进的墙钟耗时 | 所有 sim 系统预算、`sim_cli bench`、验收 A2 |
| **每渲染帧（摊销）** | 16.67 ms（60 fps） | 60fps 下平均每帧推进 0.5 个 tick → sim 摊销 = 每 tick 预算 × 0.5 | 帧预算表、玩家感知的流畅度 |
| **每渲染帧（CPU 侧）** | 16.67 ms | sim 摊销 + 渲染提交；GPU 与之并行 | 帧预算表 |

基准条件（必须写进任何性能结论）：**M1 / 8GB / 1080p / 400 单位 / rayon 线程池 = 逻辑核数 / `--release`（LTO）/ 无调试钩子**。

**A. 每 sim tick 预算（400 单位，33.33 ms 周期）**

| 系统 | 预算 | 手段 |
| --- | --- | --- |
| 感知（LOS/听觉） | 4.0 ms | 批量射线、摊还到 10Hz（每 tick 1/3 单位）、模拟 LOD 剔除、cache |
| 掩体评估 | 2.0 ms | 摊还到 5Hz、候选 top-K 剪枝（≤ 12 槽）、评分缓存 |
| 决策（指挥/班/兵） | 1.5 ms | 低频 + 事件驱动 |
| 移动 / 避让 | 1.0 ms | flow field + 局部 steering |
| 弹道 | 1.0 ms | 段射线、chunk 空间哈希、活跃投射物上限 4096 |
| 世界维护（破坏/重建） | 1.5 ms | 摊还、脏队列（每 tick 最多 2 chunk） |
| **合计** | **11.0 ms / tick** | 余量 22 ms，用于抖动与降级空间 |
| **验收口径（§90.3 A2）** | **p50 ≤ 6 ms / tick，p99 ≤ 11 ms / tick** | 与上表一致，不再另有口径 |

**B. 每渲染帧预算（60 fps，16.67 ms）**

| 项 | 预算 | 说明 |
| --- | --- | --- |
| sim 摊销（0.5 tick/帧） | 5.5 ms | = 11.0 ms × 0.5（120fps 时为 2.75ms；30fps 时为 11ms） |
| 渲染提交（CPU） | 3.0 ms | MultiMesh 合批、剔除、材质排序 |
| CPU 侧合计 | **8.5 ms** | 余量 8.17 ms |
| GPU（并行） | 5.0 ms | 与 CPU 并行，不叠加到 8.5 ms 上 |

**追帧 / 超时策略**（lockstep 下**绝不能丢 tick**，否则必然分歧）：

1. 每个渲染帧最多推进 **2 个 sim tick**（`max_ticks_per_frame`）；
2. 落后 3–30 tick：暂停渲染插值与部分表现更新，优先跑 sim，HUD 显示"追帧中"；
3. 落后 > 30 tick：触发**全局降级**（必须由所有客户端在同一 tick 同步生效，见 §10.7.1）：
   依次降低模拟 LOD 距离、关闭次要系统（弹道下坠、跳弹二次射线）、最后降分辨率；
4. 单机模式允许"慢动作"（sim 时间相对墙钟变慢）而不是丢帧；
5. 若降级到底仍不达标 → 判定该机不满足最低配置，启动时提示（而不是静默掉帧）。

### 10.7.1 两种 LOD：模拟 LOD（确定性）与渲染 LOD（表现）

> **这是 lockstep 的硬边界，不是优化细节。** 曾经的设计用"到相机距离 + 玩家是否选中"决定 AI 更新频率——
> 那会让不同玩家的镜头/选中产生不同的决策频率，进而让同一 tick 在不同客户端走到不同状态，
> lockstep 直接分歧。**任何相机/选中/UI 状态都不得进入 sim。**

| 类别 | 依据 | 允许影响 | 例子 |
| --- | --- | --- | --- |
| **模拟 LOD**（进 sim，必须各客户端一致） | **只依赖 sim 内部状态**：①该单位所在班组是否有活跃交战（contact < 30s）；②到最近"交战事件"的距离（交战事件是 sim 里的一条记录：开火/中弹/爆炸/发现敌人）；③是否被指派了任务 | AI 感知/决策频率、是否走完整动作集、是否参与射线预算 | 远离所有交战、无任务的班组 → Dormant（0.5Hz，只更新位置与存亡） |
| **渲染 LOD**（不进 sim，各客户端可不同） | 相机距离、是否被选中、是否在视锥内 | 动画骨骼数、网格 LOD、粒子、语音气泡、UI 细节、**表现层更新频率** | 屏幕外单位不更新动画，但 sim 里它照样在决策 |

具体规则：

| 模拟 LOD | 触发条件（全部为 sim 状态） | 频率 |
| --- | --- | --- |
| FULL | 班组有活跃 contact，或距最近交战事件 ≤ 80 m，或被指派任务 | 感知 10Hz / 掩体 5Hz / 完整动作集 |
| REDUCED | 距最近交战事件 ≤ 250 m | 感知 3Hz / 掩体 1.5Hz / 简化动作集 |
| DORMANT | > 250 m 且 无任务 且 无活跃 contact | 0.5Hz，只更新位置与存亡；被交战事件唤醒 |

- **"玩家关注"属于表现层**：玩家选中单位只会让 UI 显示更细、动画更全、相机跟随，**不会**让它想得更快。
- 降级时（§10.7 热节流）允许**全局**降低模拟 LOD 距离阈值——但必须通过"全局设置同步"进入 sim（即在命令流里广播一次 `lod_profile` 变更，所有客户端在同一 tick 生效），而不是各客户端自行决定。
- **确定性测试（新增 A8，见 §90.3）**：同一回放跑两遍，注入**不同的相机轨迹与不同的选中集合**（相机/选中作为纯表现输入，不参与 sim），断言两遍的逐 tick 校验和**完全相同**。这条测试进 CI，是防止后来者不小心把相机状态喂进 sim 的唯一保险。

**禁止项**（性能红线）：sim tick 内不做堆分配（用 arena/池）、不做字符串操作、不做 Godot 调用、不做文件 IO；所有日志走结构化环形缓冲（debug 构建才写盘）。

## 10.8 数据驱动与调试工具

- 所有可调参数放 `sim/data/*.ron`：`weapons.ron`（弹速/伤害/穿透/误差锥）、`materials.ron`（穿透代价/破坏阈值/声音）、`units.ron`（模板：血量、nerve、携弹、视野）、`ai_weights.ron`（掩体评分权重、威胁场权重、士气曲线）、`build_costs.ron`。开发期支持热重载（文件变化 → 重建只读表，不重启）。
- `sim_cli` 子命令：
  - `sim_cli bench --units 400 --ticks 10000`：输出各系统 p50/p99 耗时；CI 做回归阈值。
  - `sim_cli replay <file> --verify`：跑黄金回放并比对校验和。
  - `sim_cli headless --level x --script cmds.txt`：无渲染跑完一局，输出统计（伤亡、命中率、弹药消耗、投降次数）。
  - `sim_cli dump --what cover|threat|contacts --png`：把内部数据导出为可视化图（调试神器，也用于文档配图）。
- **AI 可解释性是硬需求**：任何决策都能回答"他为什么这么做"（当前任务、候选掩体评分 top-3、威胁方向、contact 源、被否决的原因）。UI 与 CLI 都要能展示。

## 10.9 网络（Lockstep）

- 输入只有"命令"（玩家下达、低频、小体积）→ 天然适合 lockstep。
- 每个客户端在本地跑完整 sim；命令附带执行 tick = 当前 tick + `input_delay`（默认 6 tick ≈ 200ms，可调；被压制/距离远时增加，模拟"无线电传递"延迟，且是玩法的一部分）。
- 每 tick 广播命令（可靠有序），收到落后 tick 的命令 → 请求对端重传；超过窗口未收到 → 暂停（stall）等待（显示"等待指挥网络"）。
- **校验和**：每 30 tick 广播 sim 状态哈希；不一致 → 立即保存分歧点前后 60 tick 的回放并断线（用于定位不确定性 bug，这是选定点数最大的回报）。
- **快照**：每 1800 tick（60 秒）存一次全量压缩快照（差量 + zstd），用于观战加入与断线重连（重连 = 拉最近快照 + 追帧）。
- 合作模式：2 名玩家共享一个阵营的控制权，命令合并进同一命令流，权限可配置（全局 / 按班组 / 只读观察）。
- 对战模式：同上，各自阵营。
### 10.9.1 信息可见性：模拟无秘密，呈现有迷雾（R2）

> 原设计同时承诺了两件互斥的事：一边说"每个客户端运行完整模拟"（lockstep 的必然结果），
> 一边说"感知系统区分 SEEN/HEARD/RADIO/INTEL，玩家只知道单位观察到的敌情"。
> 客户端持有敌方完整状态时，未发现的敌军和敌方指挥层黑板都能被读到，**校验和无法阻止信息泄露**
> （校验和只能证明"没人篡改模拟"，不能证明"没人偷看"）。必须明确取舍。

**裁定：**

| 层 | 是否保密 | 说明 |
| --- | --- | --- |
| **模拟层** | **不保密** | lockstep 必然结果：每个客户端持有全量状态。这是选 lockstep 换来的（回放、断线重连、零服务器成本），代价必须承认 |
| **呈现层** | **有战争迷雾** | 只有己方单位感知到的敌人被渲染、被显示在 UI/雷达上；未发现的敌人不渲染。这是**玩法**，不是安全边界 |
| **反作弊承诺** | **只承诺"不篡改"，不承诺"防偷看"** | 校验和 + 分歧即断线，可保证对局公平（不能改自己的兵）。但**内存读取类信息泄露（maphack）无法防止**——这是 StarCraft/AoE 等 lockstep RTS 的固有取舍，写进 FAQ 而不是假装没有 |

对既有系统的影响：

- **侦察与情报的价值不来自"技术保密"，而来自"认知成本"**：玩家看到的是已过滤的战场（呈现层迷雾），
  情报（俘虏口供、侦察）的作用是把"敌方指挥层的决定"直接送到你面前，省掉你派人去查的时间和伤亡。**价值依然是真实的。**
- **俘虏口供（§40.2.3）**：读的是敌方**指挥层的 objective 与统计**（还剩多少人、下一步打哪、弹药存量），
  **不是**每个单位每 tick 的实时意图。这在设计上也更合理：一个俘虏知道连长要干什么，不知道每个班此刻的坐标。
  实现上它读的是同一份本地数据（lockstep 下本来就在内存里），因此**不需要额外机制**，只需把它写清楚。
- **不做的东西（1.0）**：权威服务器 + 按玩家过滤的状态同步。那会把架构从 lockstep 换成 server-authoritative，
  代价是放弃 bit-exact 回放、断线重连变复杂、需要服务器运维。**记入 2.0 候选**：
  只有当"隐藏部署/隐藏科技"成为核心玩法（例如叛军地道伏击必须真正不可知）时才重新评估。
- 若要让步：在**单人/合作**模式下，呈现层迷雾对玩家是"诚实的"（你确实不知道）；
  在**对战**模式下，对手可能用内存读取作弊——接受它，并把举报/黑名单作为缓解手段。
